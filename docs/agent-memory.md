# LunaTranslator project memory

Contract version: `lunatranslator-memory/1`.

## Authority and entrypoint

Read this complete contract before substantive LunaTranslator work, including
work outside this checkout, and before project memory I/O. Read it again after
resume or compaction when its contents are missing, and when it changes.
This file exclusively owns the project's memory lifecycle. A skill or host
baseline must not supplement its silent portions with another lifecycle.
Missing instructions or an unavailable service do not activate another owner.

Current explicit instructions and current primary evidence outrank memory.
Memory supplies context to verify; it does not grant permission to change code,
merge upstream, publish, deploy, spend money, or execute a stored arrangement.
Repository instructions, source, tests, documentation, configuration and live
outputs retain their own authority.

## Provider binding and scope

The logical memory owner is **LunaTranslator**, with project scope
`wing_lunatranslator`. Resolve its actual provider and exact tool namespace
from an explicit client binding supplied outside the repository. The binding
must identify this owner and scope and map the operations below to compatible
tools. A similarly named server, shared backend or accessible wing is not a
binding. Do not infer the binding from another project's configuration.

Before first I/O, inspect the exact tool metadata and schemas. Require a safe
health/status read; scoped thematic search; complete record retrieval by ID;
bounded room/record listing with pagination; duplicate checking; addition with
a returned ID; and readback of destination and content. Existing-record
changes additionally require the exact corresponding mutation and verification
operations. Use actual schemas rather than guessed parameter names. If a
required operation, exact scope filter or binding is missing, report the gap
and stop dependent memory I/O and work. Tool availability is not write authority.

Project queries must be filtered to `wing_lunatranslator` before retrieval
because the bound backend may contain unrelated owners. Start with a thematic
query and a bounded increased limit, normally 20 when supported. Do not perform
a whole-backend search that exposes other owners without their separate access
authority. A healthy empty scope is not an outage; its first eligible record
may create it. Never create empty rooms or placeholder records.

Use these rooms according to the conclusion's subject:

## Ownership and useful sources

This project owns LunaTranslator-specific decisions and knowledge, including
integration of other games, capture adapters, translation behavior, compatibility,
validation and operational lessons. It is a cross-game software project; it
does not own game playthroughs, lore, player progress or unrelated preferences.

Before each substantive subtask, resolve separately:

1. Which authorized sources could provide relevant experience.
2. Which owner may save each new conclusion.
3. Where any recalled rule actually applies.

Select useful project experience even in external or cross-project work. The
working directory and eventual result owner are not recall boundaries. Load
each concretely related source owner's complete required contract before its
I/O and follow its access, privacy, version, spoiler and outage rules. A tunnel
is not required. Reading another owner's experience does not import its rules,
enroll this repository, or transfer ownership of its facts.

Independently owned cross-project engineering knowledge and other subjects
follow their own contracts. Do not copy or paraphrase project facts into another
owner as purportedly independent knowledge. One fact has one owner. Project
records must remain usable without inaccessible private records from another
owner; use authorized primary evidence instead. When ownership is ambiguous,
resolve it before writing. An unavailable owner is not permission to choose a
different destination or lifecycle.

## Recall before dependent work

Before initial domain analysis and every substantive subtask, including an
autonomous pivot, identify the subjects and intended operation, method or tool.
Check coverage for each need and its primary and concretely related authorized
sources. Search every uncovered need before dependent analysis or action,
regardless of confidence or expected usefulness. A new failure, method or tool
can create a new need within the same subject. Instruction and primary-source
reads needed to identify the task and boundaries may precede recall.

1. Confirm the binding and required tool surface, then establish service health.
   A status call alone does not establish substantive coverage.
2. Search the project scope thematically. Refine noise, archive-heavy results or
   an uncovered related topic with evidence-seeded wording or room filters.
   Do not impose a mandatory query per room.
3. Fetch complete relevant records by their actual IDs before relying on them.
   Search snippets, rankings and previews are candidate discovery only. Resolve
   a missing ID through a bounded scoped listing; never invent it.
4. After a miss on an established topic, try alternate wording based on actual
   evidence and inspect relevant bounded listings, following pagination. A top-k
   miss does not prove absence. Report unavailable sources as partial coverage.
5. Verify decision-relevant remembered claims against current primary sources,
   applicable revisions and known later changes. Keep historical findings as
   history; preserve attribution, scope, dates, uncertainty and conflicts.
6. Apply the applicable findings or explain a material conflict. A plausible hit
   on another need does not finish the current need's coverage.

Keep compact working context for each need: owner and authorized scope,
queries/refinements, fetched IDs and source locators, applicable dated findings,
uncertainty, conflicts and gaps. Distinguish **loaded and checked**, **checked
without a relevant result after refinement**, and **partial or unavailable**.
Do not create a memory activity drawer or local record inventory for this.

Reuse intact applicable coverage. A new message or elapsed time alone is not a
recall trigger. After compaction, import or handoff, restore missing
decision-critical content from its source before dependent work; a statement
that recall occurred is insufficient. Re-fetch known IDs when only their
critical details are lost rather than repeating intact discovery.

## Delegated access

The main agent owns top-level coverage and every memory mutation. In a delegated
prompt, name this complete contract, the exact client binding, any other
authorized source owners and every required runtime/reference file. Pass the
bounded task, existing complete findings, source locators, dates, uncertainty
and access/privacy boundaries. A subagent may read this project's memory only
within that delegated scope after loading those sources; it may fill uncovered
related needs only where the related owner separately permits access.

Subagents return searched needs/scopes, queries and refinements, fetched IDs and
locators, applicable findings with dates and uncertainty, conflicts, gaps, and
capture or correction candidates. The main agent checks that evidence and may
reuse complete applicable coverage. Incomplete, stale or conflicting critical
details require verification. Unresolved ownership or a required recall failure
returns immediately to the main agent and stops dependent work.

Subagents perform reads only. They must not add, amend, relocate, invalidate,
delete, link, checkpoint, write diaries or knowledge-graph facts, mine, sync,
or use a pending queue, including queue reads. Inherited tools do not grant
permission. No-memory mode also disables their memory I/O.

## Capture timing and exclusions

Before each substantively complete answer or completed discussion stage,
classify new reusable conclusions and complete their permitted capture. Do not
wait for task closure, a final choice, repeated interest, a special skill or a
separate save request. A closure pass catches omissions rather than delaying
capture. No new durable substance means no write.

Eligible content includes reusable sourced explanations, verified technical
findings, explicit project preferences or constraints, observations, meaningful
ideas, attributed hypotheses, and accepted decisions with reasons and limits.
Preserve the actual author and status; an idea remains proposed until accepted,
and a user report remains attributed until independently verified.

Source code, configuration, instructions, procedures, full plans, current task
state, complete lists, factual chronology and test results stay in their
canonical artifacts. Do not copy them into memory as competing operational
truth. Exclude routine replies and definitions, acknowledgments, internal
reasoning, isolated arithmetic, generic retellings and already-covered content.
Never store secrets, credentials, raw conversations, private game text or
translation corpora, source dumps, private logs or unrelated personal data.
Exact approval cannot waive these exclusions. A minimal safe source locator
may identify evidence without exposing its protected payload.

Apply artifact exclusion per independent conclusion, not to an entire topic.
Separately inspect useful decision context: goal, reasons, acceptance and time
evidence, scope, consequences and agreed trial/review conditions. Reuse an
artifact or complete existing record that already covers it. Otherwise capture
eligible independent context with a precise pointer to the canonical rule;
do not duplicate the rule. A successful edit or commit alone does not establish
that no eligible context was missed.

## Capture authority and verification

Only the main agent may automatically add new independent non-sensitive
project conclusions. No per-record approval is required for those additions.
This grants no implementation, instruction-change, publication, deployment,
spending or arrangement-execution authority.

Before adding, search the intended scope, fetch plausible equivalent or
conflicting records and run the bound duplicate-check operation. An equivalent
conclusion is a no-op. An equivalent existing record elsewhere remains an
existing record; do not copy it to improve its location.

Every amendment, enrichment, correction, supersession, relocation, invalidation,
link change or deletion of an existing record requires an exact preview and
explicit user approval: affected IDs, current evidence, proposed change and
destination, reason, and verification method. A factual agreement alone is not
mutation approval. Never bypass this gate with a near-duplicate addition.
Preserve valid historical versions and provenance.

Sensitive content requires an exact content-and-destination preview and
explicit approval, in addition to any amendment gate. Unresolved sensitivity
is not automatic-addition authority. Resolve it before writing, and obey the
source exclusions above. No diary, knowledge graph, tunnel, checkpoint,
mining, sync, bulk repair or secondary memory store is authorized by this
contract. Capture uses drawers/records only.

Use one independent conclusion per logical record and the actual tool schema.
Include at least these fields in the record content when the schema has no
dedicated fields:

```text
Subject: precise project topic
Conclusion: reusable substance
Use case: when it helps
Classification: verified fact | report | preference | idea | hypothesis | decision
Author and status: actual source author and supported status
Scope: applicable software/game adapter/revision and limits
Event or observation date: supported date/precision, or Unknown
Verification date: actual check date/precision, or Not verified
Evidence: precise authorized source locators and validation
Uncertainty and conflicts: supported limits, or None known
```

After each permitted addition or approved change, retrieve the returned or
affected ID and verify its scope, room, full content, provenance,
classification and absence of excluded payloads. For deletion, verify absence
by exact ID and the approved scope. Report persistence only after that readback;
identify the verified ID briefly. Separate verified operations from incomplete
ones. A write acknowledgement without readback is unconfirmed saving.

## Decisions, acceptance and action

For a decision or arrangement, include the following in the same record rather
than a separate consent ledger:

```text
Arrangement and version: precise proposal or direct instruction
Context and goal: intended outcome and constraints
Decision detail: chosen behavior and concrete consequences
Rationale and alternatives: supported reasons and considered options, or Unknown
Proposer: user | assistant
Acceptance status: proposed | accepted | rejected | revised | revoked | unknown
Acceptance evidence: minimal exact user response bound to its referent, or None
Decided at: supported acceptance timestamp/date, or Unknown
Time evidence: actual source locator, precision and timezone, or Unknown
Source: actual locator and supported context/date
Scope and duration: supported applicability, limits and uncertainty
Review conditions: agreed trial/reconsideration/rollback conditions, or None known
Revisions: actual later changes and record/source IDs, or None known
```

Keep original decision time separate from observation, verification and storage
time. Use the acceptance message's actual timestamp and timezone when supported;
if only a date is known, retain it with unknown time/timezone. A chat's creation
or update time, turn boundary, current clock, record filing time and later
readback time are not substitutes. Missing evidence remains unknown; never
invent IDs, quotes, reasons, rejected alternatives, times or consent.

A direct instruction can supply acceptance evidence. Bind terse assent only to
the specific proposal it unambiguously accepts. Silence, ignored suggestions,
summaries, tool success, handoffs and consent to save a proposal do not accept
or authorize its execution. Unknown duration does not become standing authority.
Preserve revisions, rejection and revocation rather than relying on an older
accepted label.

Before a remembered arrangement changes a response, procedure or consequential
action, verify its actual supporting source, scope and known later changes, or
establish independent authority from current instructions. A stored accepted
label or quote alone is insufficient. Reuse intact verified authority without
asking again. If historical permission cannot be verified, hold only its
dependent action and obtain clarification; independently authorized work may
continue. Current instructions apply while a record amendment awaits approval.
Check legacy evidence on use rather than silently enriching old records.

## Failure, recovery and no-memory mode

Immediately report unavailable mandatory recall/capture, missing binding or
required tool operations, and discovered omissions of mandatory memory work.
Notify before diagnosis, retry or a substantive answer, even when unrelated
work can continue. State the affected operation, observed failure or omission,
and consequence. Distinguish an unperformed or inconclusive health check from
confirmed unavailability; do not invent the cause. Report unverified saving as
unconfirmed, including a timeout that may have succeeded remotely.

Stop all work depending on the unavailable project evidence. Do not substitute
another palace, flat facts, Git history as semantic recall, a local truth
mirror, queue, outbox or pending-memory file. No project transport queue is
authorized. Do not claim a chat note is durable retention. Unrelated work
without that dependency may continue under its own authority; another owner's
healthy memory does not waive this project's stop.

After reporting, confirm the binding, scope and stale-session state. Retry one
safe status/read operation, then diagnose transport, authentication and backend
health read-only. Perform remediation only with its separate authority.
Before retrying any ambiguous write, inspect remote state and duplicates to
discover whether it succeeded; do not blindly repeat it. Preserve unresolved
operation IDs and evidence in working context without creating a store.

Resume dependent work only after observed health and required scoped recall
succeed. Report restored access separately from unfinished recall or capture.
Recheck current source, ownership, permission and duplicates before completing
an interrupted write, then verify readback. Do not claim recovery merely from
a healthy status call or a later unrelated success.

An explicit no-memory or off-the-record request disables all palace and queue
I/O, including status, delegated reads and recovery, and authorizes no implicit
artifact persistence. Explain and pause any task with a mandatory memory
dependency; this mode does not waive that dependency. Independently authorized
work without it may continue. Do not bypass this boundary through another
owner, a summary or a local copy.
